# Spec: Security Bootstrap Data

## Summary

Define the minimum security bootstrap data required before authentication, authorization, user management, and role-based UI behavior can work reliably.

This spec documents:

- Required platform roles.
- One required initial `ADMIN` user.
- Optional demo users for local/dev/test only.
- The implementation boundary between static role seed data and environment-driven user bootstrap.
- Idempotency, password, and soft-delete rules.

This spec does not implement login, JWT, Spring Security, endpoint authorization, Angular frontend behavior, or user management. It also does not modify `V1__create_initial_schema.sql`.

## 1. Purpose

Security bootstrap data is needed because the system cannot safely start user management or role-based access without known platform roles and at least one administrative account.

The bootstrap data supports future work for:

- Login and credential validation.
- JWT claims containing user and role information.
- Endpoint authorization by role.
- User management by an initial administrator.
- Angular route guards and role-based UI actions.

Without this bootstrap step, a deployed environment could have no `ADMIN` user and no required roles, making it impossible to access protected administration features after deployment.

## 2. Database Target

The existing schema is defined in:

```text
src/main/resources/db/migration/V1__create_initial_schema.sql
```

Relevant `roles` table fields:

| Column | Type | Constraint | Bootstrap requirement |
|---|---|---|---|
| id | BIGSERIAL | primary key | generated by database |
| name | VARCHAR(80) | not null, unique | required role code/name |
| description | VARCHAR(255) | nullable | human-readable role purpose |
| active | BOOLEAN | not null, default true | required roles must be active |
| version | BIGINT | not null, default 0 | default value is acceptable |
| created_at | TIMESTAMP | not null, default current timestamp | default value is acceptable |
| updated_at | TIMESTAMP | not null, default current timestamp | default value is acceptable |

Relevant `users` table fields:

| Column | Type | Constraint | Bootstrap requirement |
|---|---|---|---|
| id | BIGSERIAL | primary key | generated by database |
| role_id | BIGINT | not null, references roles(id) | must reference the `ADMIN` role for the initial admin |
| full_name | VARCHAR(120) | not null | required display name |
| username | VARCHAR(80) | not null, unique | required login username |
| password_hash | VARCHAR(255) | not null | must store a hashed password, never plain text |
| active | BOOLEAN | not null, default true | bootstrap users should be active unless explicitly disabled |
| version | BIGINT | not null, default 0 | default value is acceptable |
| created_at | TIMESTAMP | not null, default current timestamp | default value is acceptable |
| updated_at | TIMESTAMP | not null, default current timestamp | default value is acceptable |

Implementation boundary:

- `V1__create_initial_schema.sql` must never be edited for this bootstrap data.
- Required roles may be seeded later with a new append-only Flyway migration because role values are static platform data.
- A recommended role migration name is `V2__seed_required_roles.sql`.
- The initial `ADMIN` user must not be created by a static SQL migration when its password comes from environment/configuration.
- The initial `ADMIN` user should be created by an application bootstrap component that runs after Flyway.
- Optional demo users should also be created only by application/profile-controlled bootstrap logic, not by mandatory production SQL.
- The application bootstrap component must be idempotent, tested, and safe to run multiple times.
- Security bootstrap must be disableable with `security.bootstrap.enabled=false`.
- The application bootstrap component must read `SECURITY_BOOTSTRAP_ADMIN_PASSWORD`, hash it, and store only the hash.
- The application bootstrap component must not overwrite an existing `admin` user.
- If bootstrap is enabled and the `admin` user does not exist, `SECURITY_BOOTSTRAP_ADMIN_PASSWORD` is required.
- Tests must not require a real admin password; tests must either provide test properties or disable bootstrap where appropriate.

## Implementation Boundary

Static database seed data and environment-driven credential data must be handled differently.

Required roles:

- May be implemented with a new append-only Flyway migration.
- Are safe for migration-based seeding because they do not contain secrets.
- Must use conflict-safe inserts based on `roles.name`.
- Must keep existing migration history append-only.

Initial `ADMIN` user:

- Bootstrap must be disableable with `security.bootstrap.enabled=false`.
- Must not be created by static SQL if the password comes from configuration or environment.
- Must be created by an application bootstrap component after Flyway has finished.
- Must read `SECURITY_BOOTSTRAP_ADMIN_PASSWORD`.
- Must hash the password before persistence.
- Must leave an existing `admin` user unchanged.
- Must fail fast or report a clear startup error if bootstrap is enabled, the admin user is missing, and the password configuration is absent.

Optional demo users:

- Must be application/profile-controlled.
- Must require both `security.bootstrap.demo-users.enabled=true` and an allowed active profile: `local`, `dev`, or `test`.
- Must never be mandatory production bootstrap data.
- Must follow the same hashing and idempotency rules as the initial `ADMIN` user.

## 3. Required Roles

The system must contain these required platform roles.

Because the current `roles` table has `name` but no separate `code` column, the role code is stored in `roles.name`.

| Code/name | Description | Active | created_at | updated_at |
|---|---|---:|---|---|
| ADMIN | System administrator with catalog, user, report, export, and full-history access. | true | database default acceptable | database default acceptable |
| SUPERVISOR | Shift supervisor with operational catalog read access, daily movement visibility, reports, history, reception registration, and reception approval/cancel permissions when required. | true | database default acceptable | database default acceptable |
| OPERADOR | Production operator allowed to register receptions, cutting records, scrap, molding output, and view own current-shift history. | true | database default acceptable | database default acceptable |
| CONSULTA | Read-only user allowed to view reports and history without registering operational movements. | true | database default acceptable | database default acceptable |

Role behavior summary:

- `ADMIN` can manage catalogs, manage users, view all reports, export data, and view full history for any lot or container.
- `SUPERVISOR` can view catalogs but not modify them, view daily movements, view shift/global reports, view full history, register receptions, and approve or cancel receptions if needed.
- `OPERADOR` can register receptions, cuts, scrap, and molding output, and can view only their own current-shift history.
- `CONSULTA` is read-only for reports and history and cannot register operational movements.

Required roles are platform data, not optional user-entered catalog records. Production deployments must not depend on someone manually creating them after release.

Recommended implementation:

- Seed these roles with `V2__seed_required_roles.sql` or equivalent append-only migration.
- Do not include users or password hashes in that role seed migration.

## 4. Required Initial Admin

The system must define one required initial admin account so a new deployment can be accessed.

Required initial admin user:

| Field | Value/rule |
|---|---|
| username | `admin` |
| full_name | `Initial Administrator` or another safe non-personal placeholder |
| role | `ADMIN` |
| active | `true` |
| password_hash | generated from an injected password, never from hardcoded source text |

Password handling rules:

- The future implementation must read the initial admin password from configuration or environment variables.
- A recommended configuration key is `SECURITY_BOOTSTRAP_ADMIN_PASSWORD`.
- Bootstrap must be disableable with `security.bootstrap.enabled=false`.
- If bootstrap is enabled and `admin` does not already exist, `SECURITY_BOOTSTRAP_ADMIN_PASSWORD` is required.
- The initial admin must be created by an application bootstrap component after Flyway has completed.
- The initial admin must not be created by a static SQL migration when its password is supplied by environment/configuration.
- The password must never be committed in source code, migrations, logs, tests with real secrets, or documentation.
- The password must be hashed before storage in `users.password_hash`.
- Plain text passwords must never be stored in the database.
- The hashing algorithm and encoder belong to a future auth/security spec.
- If `admin` already exists, the bootstrap component must not overwrite its role, full name, password hash, or active state unless a future spec explicitly changes that rule.

The initial admin user exists only to unlock the system after deployment. After user management is implemented, normal user lifecycle operations should be performed by an `ADMIN`.

## 5. Optional Demo Users

Demo users are optional and must be created only for local, development, or test environments.

| Username | Full name | Role | Active | Required in production |
|---|---|---|---:|---:|
| supervisor.demo | Demo Supervisor | SUPERVISOR | true | no |
| operador.demo | Demo Operator | OPERADOR | true | no |
| consulta.demo | Demo Consulta | CONSULTA | true | no |

Demo user rules:

- Demo users must not be mandatory in production.
- Demo users must be profile-controlled or environment-controlled.
- Demo users require both `security.bootstrap.demo-users.enabled=true` and an allowed active profile: `local`, `dev`, or `test`.
- Demo users should be created by the same application bootstrap flow, or a closely related profile-controlled component, after Flyway has completed.
- Demo users must not be created by mandatory production SQL.
- Demo passwords must follow the same no-hardcoded-secret rule as the initial admin password.
- Demo passwords must be hashed before storage.
- Real supervisors, operators, and consulta users should normally be created later through the user management module by an `ADMIN`.

## 6. Idempotency Rules

The future implementation must be safe to run more than once.

Required behavior:

- Creating required roles must not create duplicates.
- Creating the initial admin user must not create duplicate users.
- Role idempotency should be based on the unique `roles.name` field.
- User idempotency should be based on the unique `users.username` field.
- If the database supports it, prefer conflict-safe insert behavior such as insert-on-conflict by unique field.
- The role seed migration may update required role descriptions and enforce `active = true`, but it must not touch users or passwords.
- The initial admin must not overwrite an existing `admin` user unless the implementation explicitly documents and tests that behavior.
- If an `admin` user already exists, the bootstrap should normally leave it unchanged and report or log that it already exists.
- If a required role exists but is inactive, the future implementation must explicitly define whether it reactivates it or fails fast; silent accidental behavior is not acceptable.
- Demo users must follow the same idempotency rules and must only run in approved non-production environments.

## 7. Domain And Security Rules

- Roles are required platform catalog data.
- Users receive permissions through their assigned role.
- Roles and users must use `active = false` for deactivation, not physical delete.
- Default roles should be protected from accidental deletion or deactivation.
- If default role deletion is allowed later, it must be an explicit administrative policy with safeguards.
- Initial passwords must never be committed.
- Passwords must be hashed before storage.
- `users.password_hash` must never contain plain text.
- Add only `spring-security-crypto` for BCrypt hashing.
- Do not add Spring Security web configuration, login, JWT, filters, endpoint authorization, or frontend code.
- Endpoint authorization will later consume role names such as `ADMIN`, `SUPERVISOR`, `OPERADOR`, and `CONSULTA`.
- Angular route guards and role-based UI actions will later consume the same role model through authenticated user context or JWT claims.
- This spec defines bootstrap data only; it does not define the complete permission matrix for every endpoint.

## 8. Future Use Cases

This spec does not implement auth yet, but the bootstrap data will later support:

- User management.
- Login.
- JWT claims.
- Endpoint authorization.
- Angular route guards.
- Role-based UI actions.
- Report and history access control.
- Operational registration permissions.

Future specs should define:

- `_specs/users.md` for user lifecycle, role assignment, active/inactive behavior, and administrative user management.
- `_specs/auth-jwt.md` for login, password verification, password hashing, JWT generation, JWT validation, and claims.
- `_specs/endpoint-authorization.md` for mapping roles to REST endpoints and operational actions.
- `_specs/angular-rbac.md` or equivalent frontend spec when the Angular frontend is introduced.

## 9. Acceptance Criteria

1. The four required roles `ADMIN`, `SUPERVISOR`, `OPERADOR`, and `CONSULTA` are documented as required platform data.
2. Required roles are active by default.
3. Required roles use `roles.name` as the role code because V1 has no separate role code column.
4. One initial `ADMIN` user can be created safely.
5. The initial admin username is `admin`.
6. The initial admin references the `ADMIN` role.
7. The initial admin is active by default.
8. The initial admin password is not hardcoded in source code or migration text.
9. The initial admin password is injected from configuration or environment.
10. Passwords are stored only as hashes in `users.password_hash`.
11. Required roles may be seeded by a new append-only Flyway migration.
12. The initial admin user is not created by static SQL when its password comes from configuration or environment.
13. The initial admin user is created by an application bootstrap component that runs after Flyway.
14. The application bootstrap component reads `SECURITY_BOOTSTRAP_ADMIN_PASSWORD`.
15. The application bootstrap component does not overwrite an existing `admin` user.
16. Bootstrap can be disabled with `security.bootstrap.enabled=false`.
17. If bootstrap is enabled and the `admin` user does not exist, `SECURITY_BOOTSTRAP_ADMIN_PASSWORD` is required.
18. Tests do not require a real admin password; tests use test properties or disable bootstrap where appropriate.
19. Optional demo users are documented for `SUPERVISOR`, `OPERADOR`, and `CONSULTA`.
20. Optional demo users are created only when `security.bootstrap.demo-users.enabled=true` and the active profile is `local`, `dev`, or `test`.
21. Optional demo users are application/profile-controlled.
22. Demo users are not required in production.
23. Real non-admin users are normally created later through the user management module by an `ADMIN`.
24. Bootstrap implementation is idempotent and does not create duplicate roles or users.
25. Existing roles and users are not overwritten unless a future implementation explicitly documents and tests that behavior.
26. Roles and users use soft deactivation through `active = false`.
27. Default roles are protected from accidental deletion or deactivation.
28. Only `spring-security-crypto` is added for BCrypt hashing.
29. Spring Security web config, login, JWT, filters, endpoint authorization, and frontend code remain out of scope.
30. `V1__create_initial_schema.sql` remains unchanged.
31. Future users/auth modules can reference the required roles by name and users by role assignment.

## 10. Out Of Scope

This spec explicitly excludes:

- Login endpoint.
- JWT generation.
- JWT validation filter.
- Password reset.
- Password hashing implementation details.
- Full user management UI.
- Full user management backend.
- Endpoint authorization rules implementation.
- Spring Security configuration.
- Spring Security web configuration.
- Login, JWT, filters, endpoint authorization, and frontend code.
- Angular frontend.
- Angular route guard implementation.
- Changing existing Flyway migrations.

The next step after approval should be creating an implementation plan for this spec, not writing implementation code immediately.
